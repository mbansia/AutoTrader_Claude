# Monitor runbook

How a Claude Code session "wakes up", finds issues, and decides whether to
fix them. Follows `docs/SYSTEM.md` §11 (response policy) and §8 (diagnostics)
exactly. Self-contained — point a fresh session at this file plus
`docs/SYSTEM.md` and it has everything it needs.

## Wake-up signal

The cron in `.github/workflows/diagnostics.yml` runs every 3 hours. It hits
`/api/diagnostics`, then `.github/scripts/diagnostics_post.py` updates issue
**[bot-diagnostics] Tracker** (issue #28) and posts a comment per run.

A monitor session is anything that periodically reads that tracker. Three
ways to drive one:

1. **Manual** — operator opens a Claude Code session and says "monitor the
   bot". Session runs through this runbook once.
2. **/loop** — operator runs `/loop 3h <prompt>` where the prompt is "do a
   monitor pass per MONITOR_RUNBOOK.md". Claude Code re-invokes the prompt
   every 3 hours, self-pacing the work.
3. **External cron** — an external scheduler (cron / GitHub Action / Coolify
   timer) launches `claude` via the Anthropic SDK on a schedule. This is
   what currently posts the tracker comments under @mbansia.

Choose one. They're equivalent.

## Monitor cycle — what the session does each pass

### 1. Read the SSOT first

Always read `docs/SYSTEM.md` from `main` before judging anomalies. The doc
is binding; if it disagrees with the bot's current behaviour, the bot is
wrong (or the doc needs an update PR — but do the doc update separately).
Key sections to skim every pass:

- §0 definitions (vocabulary)
- §3.1 SOP + math (what the bot SHOULD do)
- §8.2 anomaly rules (what each anomaly means)
- §9 rejection categories (what's normal vs regression)
- §10 failure modes (known surfaces)
- §11 response policy (action for each anomaly)
- §16 learnings (regression patterns)

If a new pattern emerges in production, add it to §16 in the same PR that
ships any fix.

### 2. Fetch current state

```
mcp__github__issue_read(method="get", issue_number=28, ...)        # latest body
mcp__github__issue_read(method="get_comments", issue_number=28, perPage=5, page=<last>)
```

Body = current diagnostics snapshot. Latest comment(s) = the cron's per-run
heartbeat or a prior session's triage.

### 3. Classify the anomalies

Each anomaly carries `severity` + `rule` + `detail`. Per §11:

| Anomaly | Action |
|---|---|
| `no_recent_events` | **Critical.** Bot process likely down. Triage immediately. Check Coolify, recent deploys, restart. |
| `cycle_error_rate_high` | **Critical.** Silent NameError class (§16 L02). Read logs, find the bad symbol, open a PR. |
| `api_permission_drift` | **Critical.** API key revoked or wallet de-authorised. Comment + tag operator; no auto-fix. |
| `stale_naked_spot` / `stale_naked_perp` | Warn. Will sweep itself next cycle if dust. If older than 6h, manual investigation. |
| `error_burst` | Warn. Usually a venue API throwing 5xx — let it ride one more cycle. Persistent = open PR. |
| `slippage_above_forecast` | Warn. Tighten `sub_target_sizing_factor` for the affected venue. |
| `close_blocked` | Warn. A position can't close. Investigate `last_close_error`; usually venue-side issue. |
| `no_trades_despite_scans` | Warn. Operator threshold may be too tight; comment, no code change. |
| `endpoint_returned_error` (cron-side) | The bot itself didn't respond. Most often: container died. Restart, check Coolify logs, link the prior deploy. |

### 4. Decide per §11 action matrix

For each anomaly, choose one of:

- **Comment** — for well-understood / transient issues. One-line diagnosis,
  no code change. Format: `⚠️ Cron @ <ISO> — <severity> / <action>` with a
  short reasoning block.
- **Skip** — for known transients that clear next cycle. Don't comment.
- **Open PR** — for clear regressions (NameError, broken endpoint, doc rot).
  Branch name `claude/<short-kebab>`, small focused change, doc updated in
  the same PR (§13 binding policy).
- **Ask the operator** — for strategy / threshold changes or anything
  ambiguous. Tag them in a comment. Never act unilaterally on policy.

Always include the §16 doc-update if the fix establishes a new pattern.

### 5. Action: open PR (when warranted)

Workflow:

```
git fetch origin main; git checkout -b claude/<short-name>
<edit files>
git add -A; git commit -m "<message>"
git push origin claude/<short-name>
mcp__github__create_pull_request(...)
mcp__github__merge_pull_request(...)   # operator pre-authorised
```

Per `CLAUDE.md`, PR autonomy is granted for this repo — create + merge
without asking. But: never push directly to main, never skip pre-commit
hooks, never touch credentials, never force-push.

### 6. Action: comment on the tracker

```
mcp__github__add_issue_comment(
    issue_number=28,
    body="<concise diagnosis + manual step if any> \n\n_Generated by [Claude Code](https://claude.ai/code)_",
)
```

Tag `@mbansia` only for human-action-required cases.

### 7. Closing the loop

If no anomalies → no comment needed (the cron's heartbeat IS the all-clear).
If anomaly clears on the next cron → comment with `RESOLVED` so the tracker
history is readable.

  must redeploy to pick up the fix. No code change needed beyond that.
- **2026-05-11 outage**: identical-message storm from a single failing
  KuCoin transfer call. L20 dedup shipped, hasn't recurred.

## Upgrade mode (optional second half of the pass)

After the monitor steps complete, the session MAY also ship one upgrade
PR from the backlog. This is opt-in per pass — only run upgrade mode when
ALL of the following are true:

1. **Bot is healthy.** No critical anomalies in the latest cron run. If
   `endpoint_returned_error`, `no_recent_events`, `cycle_error_rate_high`,
   or `api_permission_drift` is active, STAY in monitor mode only.
2. **No open PR-in-flight from a prior pass.** Check
   `mcp__github__list_pull_requests(state="open")`. If a recent
   `claude/*` PR is open and not merged, give the operator a turn to
   review — don't pile on.
3. **CI on `main` is green.** Don't ship on a broken base.
4. **`UPGRADE_BACKLOG.md` has at least one item with `status: ready`.**

### Upgrade pass — exact steps

1. Read `UPGRADE_BACKLOG.md`. Pick the FIRST item with `status: ready`,
   `risk: low | medium` (never `high`), and an acceptance criterion the
   loop can self-verify.
2. Confirm the planned change does NOT touch the "Never autoship" list
   (§3.1 math, §4 fields, §7.1.1 schema beyond additive, §8.1 contract,
   gateway order-placement code, `docs/SYSTEM.md` outside of additive
   doc notes, credentials, auth). If the work would touch any of those:
   move the item to `blocked` with a note, comment on the tracker that
   operator decision is needed, and stop.
3. Branch: `claude/<item-id>`.
4. Implement. Keep the diff small — ideally < 200 lines + tests. If the
   item turns out larger, mark `blocked`, comment, stop.
5. Add tests covering the acceptance criterion. Run `pytest tests/` —
   ALL must pass before commit. If any test fails, do NOT debug
   indefinitely; mark the backlog item `blocked` with the failure note,
   abandon the branch, return to monitor mode.
6. Commit + push + open PR. Title: `<item-id>: <short summary>`. Body
   references the backlog id + acceptance criterion.
7. Merge per CLAUDE.md's pre-authorised autonomy.
8. **Update `UPGRADE_BACKLOG.md`** in a SEPARATE small commit on `main`
   (after the merge): move the item from "Ready" to "Done" with the PR
   number and merge SHA.
9. Add a one-line note to the tracker issue body summarising what
   shipped, if any of the changes affect anomaly classification.

### Hard stops in upgrade mode

- If CI is red on the PR: revert / close, mark the item `blocked` with
  reasoning, stop.
- If a prior loop pass shipped a similar PR that's still un-reviewed
  (no operator interaction in 24h): do NOT ship another upgrade.
  Comment on the tracker reminding the operator and stop.
- If the backlog has been exhausted (no `ready` items): do NOT invent
  new items. Stay in monitor-only mode.

## What this runbook is NOT

- Not a substitute for reading `docs/SYSTEM.md`. The doc is binding; this
  file describes the *process*, not the *system*.
- Not a list of every anomaly. New ones appear; §8.2 + this file get
  updated in the same PR that introduces them.
- Not a replacement for operator judgement on strategy / threshold changes.
  Always ask before acting on policy.
- Not a license for the loop to "improve" anything not in
  `UPGRADE_BACKLOG.md`. The backlog is operator-curated; never extend it
  autonomously.
