# Runbook — AutoTrader_Codex

How an agent runs one pass of AutoWorker. Self-contained: point a fresh
agent session at this file plus `MASTER_DIRECTIVES.md` and the tracker
issue (#0) and it has everything it needs.

> Generated from the [AutoWorker](https://github.com/mbansia/AutoWorker)
> template. Edit for project specifics. The two-part shape is canonical.

The agent reads `MASTER_DIRECTIVES.md` §0.5 (operating persona — CTO,
PM, Founder CEO, QA, Marketer) and §0.6 (operating principles — respect
project prefs, five-pass persona audit before merge, new branch always,
`[ ]` checklists) on every pass. They apply throughout.

---

## Wake-up

A pass starts in one of three ways:

1. **Scheduled** — `.github/workflows/autoworker_loop.yml` runs at
   `0 * * * *` and invokes the agent CLI configured by your
   adapter (`adapters/claude_code.md`).
2. **`/loop`** — for Claude Code: `/loop 1h "do one
   AutoWorker pass per RUNBOOK.md"`.
3. **Manual** — operator opens an agent session, says "do an autoworker
   pass".

The data ingestion cron (`.github/workflows/autoworker_data.yml`) runs
on the same cadence and updates the tracker issue body + posts a
heartbeat comment. The comment fires the webhook that wakes scheduled
sessions where applicable.

## Part A — Monitor (always runs)

### A1. Read direction

Read `MASTER_DIRECTIVES.md`. Pay attention to:

- §1 goals (what success looks like)
- §7 signal criteria (how to classify what's on the tracker)
- §8 guardrails (what you cannot autoship)

If §§1–§8 changed since the last pass, recalibrate before acting.

### A2. Read tracker

Use `mcp__github__issue_read` (or the equivalent for your agent) to fetch:

- Issue body (full state — anomalies, signals, metrics)
- Last 5 comments (the cron heartbeats and prior agent comments)

Tracker issue: **#0** (label `autoworker-tracker`).

### A3. Classify signals

For each signal on the tracker, decide one action.

Default action matrix — extend per project:

| Signal class                         | Default action                                                           |
|--------------------------------------|--------------------------------------------------------------------------|
| Critical anomaly (service down, data loss risk) | Comment on tracker. Do NOT autoship a code fix unless cause is unambiguous. |
| Regression with clear cause          | Open PR (Part B candidate).                                              |
| Repeated user complaint              | Promote to `UPGRADE_BACKLOG.md` Hints. Comment.                          |
| Security advisory / CVE on a dep     | Open PR if additive (dep bump); escalate if it touches §8.               |
| CI red on main                       | Comment. Hold all Part-B shipping until green.                           |
| Doc drift (broken link, stale ref)   | Open PR.                                                                 |
| Social signal (mention, review)      | Summarise in tracker comment. Promote to Hints only if recurring.        |
| Endpoint unreachable                 | Comment with operational diagnosis. NOT a code regression.               |
| Unknown / ambiguous                  | Comment "investigation in progress". Queue for next pass.                |

**Skip duplicates.** If an anomaly was triaged in a prior pass and is
still on the tracker, do not re-comment unless 3+ cron cycles have
elapsed.

### A4. Comment format

```
⚠️ Pass @ <ISO timestamp> — <N critical / M warn / action taken>
<one-paragraph diagnosis, citing the directive section that applies>
<Manual step: ...>   (only when operator action is needed)
---
_Generated by <agent name> per RUNBOOK.md._
```

For an all-clear pass with no anomalies and no action: post nothing.
The cron heartbeat is the all-clear signal.

## Part B — Autopilot (only if Part A is clean)

**Skip Part B entirely if ANY of these are true:**

- A critical anomaly is active
- An open `autoworker/*` PR has had no operator activity in 24h
- CI on main is red
- Operator pushback (unmerge, disagree-comment, manual revert) within
  the last 3 passes
- More than one open un-reviewed `autoworker/*` PR

If all four are false, find ONE thing to ship.

### B1. Work-selection surfaces (priority order)

1. **Anomaly-driven bug fix** — regression detected in Part A with a
   clear cause.
2. **`UPGRADE_BACKLOG.md` Hints** — operator suggestions.
3. **Master directives §§1–§7 open items** — anything explicitly listed
   as a roadmap theme, perf budget, accessibility gap, doc drift, etc.
4. **Test coverage gaps** in non-§8 modules.
5. **Code quality** — dead code, TODO/FIXME, lint waivers without
   reasons.
6. **Doc drift** — broken links, stale section refs, outdated examples.

If no surface yields a safe candidate, stay in monitor-only mode. Do not
invent work.

### B2. Never-autoship check

Before writing code, sanity-check the candidate against
`MASTER_DIRECTIVES.md` §8.

Generic never-autoship list (always applies on top of project-specific):

- Anything in §8 of the directives
- Schema reshape beyond additive
- Frozen API contracts
- Credentials, env-var names, auth paths
- Master directives §§1–§8 (only §9 is append-only)
- This runbook's hard-stop rules

If any conflict: abandon the candidate, comment on the tracker, return
to monitor mode. Do not try to find a way around §8.

### B3. Ship

Per `MASTER_DIRECTIVES.md` §0.6: new branch always; **five-pass persona
audit** before merge; track work in a `[ ]` / `[x]` checklist in the
PR description.

```
git fetch origin main && git checkout -b autoworker/<short-slug>
<edit>
<run the project's test command — ALL must pass>

# === Five-pass persona audit (per §0.6 principle 2) ===
# Run each pass independently. Do NOT collapse them into one sweep.
# Document each verdict in the PR description (one line per persona).
#
# Pass 1 — CTO:
#   - Technical correctness; diff does what the directive asked?
#   - Architecture fit — any boundary violations or layering smells?
#   - Performance — any cliffs (N+1, sync I/O on hot paths, etc.)?
#   - Security — auth, input validation, secrets handling?
#   - §8 NEVER-AUTOSHIP check: does any line cross the policy boundary?
#
# Pass 2 — Product Manager:
#   - Intent match — exactly the directive scope, no more, no less?
#   - UX side-effects — any user-visible behaviour change unintended?
#   - Scope creep — anything in the diff that wasn't requested?
#
# Pass 3 — Founder CEO:
#   - Opportunity cost — is this the right work this pass given §1 goals?
#   - Strategic risk — anything that constrains future moves?
#   - Resource allocation — proportionate effort to expected impact?
#
# Pass 4 — QA:
#   - Are tests sufficient to catch regressions on the changed surface?
#   - Edge cases — failure modes, empty/null inputs, concurrency?
#   - Reproducibility — if it breaks in prod, can the failure be reproduced?
#
# Pass 5 — Marketer:
#   - Positioning impact — does this affect how the product reads?
#   - Changelog — entry needed? Where?
#   - Public comms — anything to surface to users or upstream?
#
# Only proceed if ALL FIVE passes are clean. Any fail → amend the work
# and re-run from Pass 1.

git add -A && git commit -m "<imperative summary>"
git push -u origin autoworker/<short-slug>
<open PR via the agent's MCP / CLI — include both the [ ] / [x] checklist
 AND the five-pass audit verdicts (one line per persona) in the body>
<merge per your adapter's agent-config pre-authorisation, only if all
 five audits passed>
```

**Constraints:**

- Diff target < 200 lines + tests
- Never push to main directly
- Never `--no-verify`, never force-push, never destructive shell
- Never touch credentials or §8 surfaces
- If any test fails: abandon the branch, comment on the tracker with
  the failure, return to monitor mode. Do NOT debug-loop.
- Append a learnings entry to `MASTER_DIRECTIVES.md` §9 in a separate
  commit on main (or include in the PR if the directive change is
  trivial).
- Record the shipment under "Shipped" in `UPGRADE_BACKLOG.md`.

### B4. Maximum one PR per pass

If the first candidate succeeds, the pass ends. Operator review is the
backpressure that decides whether the next pass keeps shipping.

---

## Hard stops

- **CI red on the autoworker PR:** revert / close, comment on tracker,
  stop the pass.
- **Operator pushback** (unmerge, disagree-comment, manual revert):
  pause Part B for 3 passes.
- **Two or more open un-reviewed `autoworker/*` PRs:** stop shipping
  until the oldest gets reviewed.
- **`MASTER_DIRECTIVES.md` §8 conflict:** abandon, escalate, do not
  retry on next pass without operator change.

---

## What this runbook is NOT

- Not a substitute for `MASTER_DIRECTIVES.md`. The directives are
  binding; this file describes process, not direction.
- Not a complete list of every signal. New ones appear; the directives'
  §7 + this file's action matrix should be updated together when they do.
- Not a license to invent work. The work-selection surfaces are
  exhaustive.
